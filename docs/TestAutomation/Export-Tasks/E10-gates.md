# E10 — Apply proportional checks at lifecycle boundaries

Acceptance: host
Requires: E09

## Purpose and delivery

Deliver the full [proportional policy](../Export-Design.md#proportional-validation)
under the [master](../Export-Execution-Plan.md). Read delivered resolver/parser/
capture APIs, runner startup and terminal publication, plan preflight/closeout,
reader diagnostics and existing validation/recovery contracts.

Keep this as policy on existing results under the
[remaining delivery boundaries](../Export-Design.md#remaining-delivery-boundaries).
Reuse `plan_evidence` collection, preview/apply and authenticated resolution,
`document_checks` syntax and the existing runner/controller gates. Identify the
missing gate at each affected boundary before adding code; do not replace already
strict publication or retirement verification with a second validation engine.
E10 owns the claim/role revision binding and historical-advisory decision that
E11–E13 reuse. Extract a policy module only if actual callers need it.

Classify required references from structured consumers and owning contracts.
Perform scoped early required-closure/capacity preflight and revalidate at actual
publication/retirement. Block wrong identities, corruption, unsafe ownership,
missing active proof and newly authored broken evidence/required references.
Normalize harmless equivalent spelling/formatting and make unrelated unchanged historical loss or
optional presentation defects advisory. Bind historical classification to exact
reference/claim bytes; new or changed bad references never inherit it. Advisory
availability cannot satisfy acceptance or turn a failed check into a pass.
Keep offline plan checks independent of local historical payloads. Avoid repeated
full scans and repair sessions without changed relevant inputs. Distinguish missing,
busy, denied, integrity, stale selection, conflict, pending transaction and capacity,
with document/line, expected/actual identity and a supported recovery action.
Apply the design's claim-protection precedence: protected labels and claim bytes
stay literal. A changed target/result claim receives strict semantic validation
even if the destination is unchanged. Optional presentation anchors may be
advisory only under their declared role; evidence and required instruction links
remain blocking. Register any extracted policy module with the controller guard
and validate actual-file change detection before close-out.

## Validation and close-out

Follow the master's [mandate boundaries](../Export-Execution-Plan.md#delivery).
Reuse owner-level checks for each distinct severity/refusal and test representative
gate integrations. Do not repeat the severity matrix at every caller or assert
diagnostic formatting beyond actionable class, location and recovery information.
Exercise the applicable positive and negative boundaries in private fixtures:
trivial formatting must continue; wrong matching-looking proof must stop; unrelated
old loss must not rerun tests; that same loss as an active dependency must block.
Test a harmless presentation-only edit separately from changing `Ubuntu passed`
to `Both targets passed` at the same destination. The latter must not receive
format-only normalization, and protected queue labels must still refuse edits.
Test new optional broken anchors versus new broken required/evidence references
so advisory presentation policy cannot suppress identity or claim failures.
Test absent/conflicting consumer-role declarations and a required-to-optional
role change against the owning contract. None may inherit an old advisory or
bypass strict validation of changed claims and protected labels.
Check clean-checkout `--check` without local historical output, while required
semantic preflight still refuses the same missing proof. Check bounded diagnostics,
no secrets/authentication retry and one verification per unchanged pinned scope.
Run scoped host checks, update
current contracts to delivered policy and follow the master's owned close-out.
