# Oh No! Parent Control functional specification

This specification defines the behavior required for release acceptance on a clean, supported Ubuntu 26.04 Desktop computer. Visual styling, animation, spacing, and other presentation details are outside its scope. A release is accepted only when every applicable statement below is true.
The audience does not need to understand the technical internals: an end user must be able to follow the actions and check the results.

This document describes the installed application's current functionality.
The [system design](System-Design.md) explains implementation and technical
limits. Developer previews and test tools are outside the product specification.
A documented requirement or a runnable test is not evidence that acceptance has
passed; the [scenario catalogue](../tests/e2e/scenarios.json) records automation
readiness separately.

The product manages accounts on this computer. Once installed, its settings,
time requests, parent authentication and enforcement work locally without an
Internet connection. Online Help, website links and feedback delivery need a
working connection. Appearance preferences are included only for their controls,
saved choices and effect on access; their visual rendering remains outside scope.

Terms used below:

- **Child**: a local standard account managed by the product.
- **Parent**: a local administrator who configures or approves access.
- **Parent App**: the administrator's Screen Limits and App Limits window.
- **Child App**: the child's desktop countdown and its request form.
- **Request station**: the dedicated “Oh No! Parent Control” account on the sign-in screen.
- **Daily allowance**: the configured amount of screen time for the current local day.
- **One-time grant**: access approved for a period of elapsed time; its expiry continues while the child is locked, signed out, or the computer is suspended or off.
- **Hard blocked app**: an app whose block cannot be lifted by a time request.
- **Soft blocked app**: an app that may be included in an approved time request.

For acceptance, use ordinary account creation, sign-in, app launches and package
commands, and inspect the displayed results. Choose short allowances and grants
when observing natural expiry. Observe another user's actual app activity when
checking isolation. Internal fault handling and storage protections also need
the separate technical checks described in the system design.

## 1. Core end-to-end release acceptance

### Installation and startup

- [ONPC-CORE-INSTALL-001] On a clean supported Ubuntu computer, a parent can install the release package with administrator authentication, read the completion and reboot notice, and restart normally. After reboot the sign-in screen is usable, the request-station account is available, and the Parent App opens for an administrator. Installation preserves existing personal accounts and unrelated settings.
- [ONPC-CORE-INSTALL-002] Installation, reinstallation and upgrades reject unsupported operating systems with an explanation. The package requires Ubuntu 26.04 or newer; this specification's acceptance baseline is Ubuntu 26.04 Desktop with GNOME Shell 50. Passing the installer's operating-system check alone does not establish compatibility with a later desktop version. Other distributions and older Ubuntu releases are not accepted by the installer.
- [ONPC-CORE-INSTALL-003] Installation creates the dedicated request-station account. Selecting it from the sign-in screen opens the request-only session without requiring a child or parent password first. Parent authentication is still required to approve access. An unrelated existing account with the reserved request-station identity is preserved and blocks installation.
- [ONPC-CORE-INSTALL-004] A newly managed child starts with screen-time control off, a saved daily allowance of zero, and no app blocks. The parent chooses which restrictions to enable. The product does not create personal child or parent accounts.

### Accounts and access

- [ONPC-CORE-ACCOUNTS-001] The Parent App is available to local administrators. A personal standard account cannot open a management window or change policy by launching the executable another way. The dedicated request station offers no Parent App launch action and cannot save parent policy.
- [ONPC-CORE-ACCOUNTS-002] The Parent App and request station list current local, interactive, standard accounts. Administrator, system, remote and request-station accounts are excluded. The Parent App refreshes its list while open, so an account created after installation can appear without reopening the app. Reopen a request form to obtain its current account lists.
- [ONPC-CORE-ACCOUNTS-003] An approving parent must be a current, unlocked, local, interactive administrator. Ineligible accounts are not offered and cannot approve by another route.
- [ONPC-CORE-ACCOUNTS-004] Each child's settings and grants are independent. Changing one child's settings or granting access affects only that child, including that child's retained desktops.

### Screen-time setup and enforcement

- [ONPC-CORE-TIME-001] A parent can turn screen-time control on or off for each child and choose a daily allowance. Enable control before editing the allowance; when control is off, its saved value remains visible but cannot be edited. The Parent App offers 0, 15, 30 and 45 minutes, then half-hour steps from 1 hour through 23½ hours. Custom value accepts whole minutes from 0 through 1439. Empty, nonnumeric, negative, fractional and larger custom values are rejected without replacing the last saved allowance.
- [ONPC-CORE-TIME-002] Zero daily minutes means grant-only mode: with screen-time control on, access requires an unexpired one-time grant.
- [ONPC-CORE-TIME-003] Turning screen-time control on activates the child countdown, including in an existing desktop where activation is available, applies the selected daily allowance, clears old one-time access, and reapplies saved app blocks. An activation failure is reported as a failed change.
- [ONPC-CORE-TIME-004] Changing the allowance while control is already on applies the new daily limit and preserves the current one-time grant. Saved app blocks are reapplied, ending any temporary permission to launch soft blocked apps. Reapplying screen-time settings does not itself close running apps.
- [ONPC-CORE-TIME-005] Turning screen-time control off removes the daily restriction and child countdown and clears the one-time grant. The chosen allowance and app rules remain saved. App blocking continues independently of screen-time control.
- [ONPC-CORE-TIME-006] With screen-time control on, the Parent App shows today's remaining usable time and refreshes it while open. Its explanation distinguishes remaining daily allowance from remaining one-time access and uses the larger amount. A failed status read is retried, then shown as unavailable.
- [ONPC-CORE-TIME-007] A child with usable time can sign in or unlock using the account's normal credentials. The unlocked desktop displays remaining time in its panel, counting in seconds during the final minute. Hovering over the control explains the remaining time and how to request more time or open its options. At login and after unlocking, the Child App also checks whether an expired grant's app blocks need restoring.
- [ONPC-CORE-TIME-008] When usable time reaches zero, the child's active desktop locks. Unlocking without new time is denied or followed by renewed locking. A fresh login without time is denied. Confirmed exhaustion is explained as a time-limit restriction rather than a wrong password.
- [ONPC-CORE-TIME-009] Natural exhaustion of all usable time locks the managed child's desktop without logging the child out or closing that desktop's apps. Expiry of a one-time grant alone does not lock out a child who still has daily time. Another user's foreground session continues.
- [ONPC-CORE-TIME-010] An unexpired grant permits unlocking a retained child desktop or starting a fresh login. Returning from lock, sign-out, reboot or suspend does not restart the grant's original duration.
- [ONPC-CORE-TIME-011] Daily allowance follows recorded use during the computer's local day. “Rest of the day” grants expire at the next local midnight, including on daylight saving time transition days. A fixed-duration grant may continue past midnight.

### Application access

- [ONPC-CORE-APPS-001] App Limits lists supported launchable apps available to the selected child, including system apps and apps installed for that child. It does not substitute the parent's personal app list. Hidden launchers and unsupported launchers with no supported app target may be absent. To refresh the list after installing or removing an app, reopen Parent or switch to another child and back; the list does not refresh continuously.
- [ONPC-CORE-APPS-002] Every listed app has one access rule. The legend explains the rules and the difference between precise and pattern matching.
- [ONPC-CORE-APPS-003] **Always Allowed** removes that entry's app block. Launchers sharing an executable or app identity share enforcement: allowing one entry does not override another entry's block on the same target. Always Allowed does not exempt the child from screen-time limits or unrelated operating-system restrictions.
- [ONPC-CORE-APPS-004] **Hard Blocked** prevents supported launches until a parent changes the rule. Approving more time cannot remove that block.
- [ONPC-CORE-APPS-005] **Soft Blocked** prevents supported launches normally. A request that explicitly includes soft blocked apps can temporarily permit them.
- [ONPC-CORE-APPS-006] Selecting an access rule saves it automatically. Changing an app from allowed to blocked, or from soft to hard blocked, closes matching apps already running as the selected child across that child's retained desktops. Saving an unchanged block does not close every previously blocked app. Other users' apps remain open. These rules apply with screen-time control on or off.
- [ONPC-CORE-APPS-007] Blocking prevents use of a supported app, not just discovery of its launcher. A supported native executable is blocked through its app-grid entry, desktop launcher, file manager and command. Supported Snap and Flatpak launches follow their app identities.
- [ONPC-CORE-APPS-008] Precise matching covers the app's resolved executable or supported app identity. For executable paths containing spaces or commas, identical executable copies can share the native block. A same-directory filename pattern can cover versioned AppImage files. Existing nonmatching executables remain usable when the pattern can be applied; a newly added nonmatching file may need the periodic refresh before becoming usable. A pattern that cannot safely preserve existing nonmatches is rejected with a save error.
- [ONPC-CORE-APPS-009] Blocking covers the supported targets selected in App Limits. It is not universal control of copied or renamed programs, scripts using shared interpreters, unsupported shared launchers, websites or remote devices. There are no per-app time quotas, website filters or remote-management features.
- [ONPC-CORE-APPS-010] Saving an app rule resolves an installed app's current target again, so an update between display and save does not leave the rule on its old executable. A disappeared app's saved rule is retained. Custom wildcard choices remain remembered when access changes to Always Allowed. Saving the detected default or choosing Reset to Default removes the custom override. Current limitation: when an app has a suggested version pattern, reopening Parent, reselecting the child or restoring controls after a failed save displays that pattern even after a precise override was saved. A subsequent app-policy save can apply the displayed pattern; reselect the intended precise rule before saving.
- [ONPC-CORE-APPS-011] Approving soft apps removes only soft blocks from the launch policy. Natural grant expiry does not immediately restore soft-app launch blocks or close open apps. If daily time still permits desktop use, approved soft apps remain launchable until a restoring action occurs. When the child next enters or unlocks the desktop with that grant still expired, the app restores hard and soft blocks and closes matching apps. A current replacement grant preserves the policy and running apps established by its approval. Revocation, an app-policy save, or reapplying screen-time settings also restores the complete saved launch policy; running-app effects follow the operation's own rules.
- [ONPC-CORE-APPS-012] A parent can search apps by name, description or launcher identifier and combine that search with Match Rule and Access Rule filters. Each filter accepts multiple choices or no choices; choosing none shows no apps without changing policy. The match editor offers Save, Cancel and Reset to Default. A precise rule must identify that app's target; a filename alone is accepted when its app directory is unambiguous. Patterns use filename wildcards in that same directory, with a version-independent default suggested for recognized versioned AppImages. Cancel discards the draft; Reset immediately saves the detected default. Empty or unrelated precise rules keep the editor open with an explanation. A rejected pattern save closes the editor, reports failure and reloads the last confirmed choices, subject to the precise-rule limitation above.

### Requesting and approving access

- [ONPC-CORE-REQUEST-001] A child can select the remaining-time panel control to open the fullscreen request form over their desktop. The child identity is fixed to the signed-in child. Opening it repeatedly does not create multiple request overlays.
- [ONPC-CORE-REQUEST-002] The dedicated request station uses the same form and lets the requester select a child. It provides no general desktop, terminal, file browser or parent-management window.
- [ONPC-CORE-REQUEST-003] Both forms explain when screen-time control is off for the selected child and disable submission. This is the installed forms' availability rule.
- [ONPC-CORE-REQUEST-004] The duration choices are 5, 15 and 30 minutes; 1, 2 and 4 hours; Rest of the day; and Custom value. Custom values from 0.1 through 1440 minutes are accepted and rounded to whole seconds. Use a decimal point for fractional minutes. Empty, nonnumeric and out-of-range values show validation feedback. With accounts and enabled settings loaded, Request remains available; selecting it with invalid input keeps the form open and starts no authentication. A fresh child preference selects 30 minutes with soft apps excluded and 0.1 minutes in the custom field.
- [ONPC-CORE-REQUEST-005] The requester selects an eligible parent and whether to allow soft blocked apps. The system authentication prompt identifies the child, duration and soft-app choice and requests authentication from that selected parent.
- [ONPC-CORE-REQUEST-006] The parent enters credentials only in the system authentication prompt. Product request forms do not receive, store or display the password.
- [ONPC-CORE-REQUEST-007] One successful authentication approves the complete request. It gives the requester no reusable administrator authorization.
- [ONPC-CORE-REQUEST-008] A fixed-duration request adds its amount to the larger of the remaining daily allowance and remaining one-time grant. For example, 10 daily minutes and 20 grant minutes plus a 5-minute request give about 25 usable minutes at approval, allowing for elapsed time. Rest of the day instead replaces one-time access with access until the next midnight, even when the previous fixed grant extended later.
- [ONPC-CORE-REQUEST-009] Approval applies both the time grant and the chosen app policy before showing success. The form's estimate is advisory; approval recalculates using current balances. The granted interval is measured from the approval-time calculation and continues during completion and the confirmation screen.
- [ONPC-CORE-REQUEST-010] Approval without “Allow soft blocked apps” restores hard and soft blocks and closes matching apps running as the selected child before making the new grant available.
- [ONPC-CORE-REQUEST-011] Approval with “Allow soft blocked apps” does not close open apps. Even an already-open hard blocked app remains open, although hard-block rules continue to prevent new supported launches.
- [ONPC-CORE-REQUEST-012] Requests affect only the selected child. Other users' apps remain open.
- [ONPC-CORE-REQUEST-013] Rejected authentication shows “Request denied” with the choices available for retry. Cancelling authentication returns silently to the same form. Locking, switching away from or ending the requesting session while authentication is pending cancels that request, as does closing the requesting app's connection; a later authentication result cannot revive it. Returning to the form requires a new request and authentication.
- [ONPC-CORE-REQUEST-014] Cancel or Escape closes the child overlay or returns the request station to sign-in when no authentication is in progress. During authentication, use the system prompt's cancellation action before leaving the form.
- [ONPC-CORE-REQUEST-015] Approval shows a confirmation with an immediate exit action and a three-second countdown, then closes the overlay or returns the request station to sign-in automatically. The granted time is already running during this countdown.
- [ONPC-CORE-REQUEST-016] Duration, custom value and soft-app choice are saved per child and shared across the two forms. The request station remembers its last selected child and parent; each child's overlay remembers its own selected parent. A remembered parent on one surface need not match the other surface. Missing or ineligible remembered selections fall back to a currently eligible account.
- [ONPC-CORE-REQUEST-017] The footer estimates usable time after a fixed-duration approval and refreshes as choices or balances change. Rest-of-day says access lasts until midnight. Loading, invalid-input, denial and waiting-for-approval messages take priority. An unavailable estimate does not prevent an otherwise valid request.
- [ONPC-CORE-REQUEST-018] The current request forms have sound and lightning disabled and expose no mute control. Previously saved child and kiosk mute choices remain separate, but cannot enable sound in this release.

### Revocation, persistence, and failures

- [ONPC-CORE-RECOVERY-001] A parent can select Revoke when the last loaded remaining-time total is positive and settings operations are idle. The action is available even when all remaining time is daily allowance and there is no active grant. A confirmation warns that blocked apps will close. Cancelling changes nothing. Confirming restores hard and soft blocks, closes matching apps in the selected child's retained desktops, and removes any grant. Unused daily time and other users' apps are unchanged; without usable time the child is restricted.
- [ONPC-CORE-RECOVERY-002] Parent settings and saved request choices survive app closure, sign-out, service restart and reboot. A grant keeps its original expiry across those events. Feedback drafts have the shorter lifetime specified below.
- [ONPC-CORE-RECOVERY-003] Restarting the settings service reasserts the child component for enabled children and rebuilds execution rules from current app filters. Updated child/request components may require renewed sessions or reboot as directed by the package. Service restart alone does not restart every already-running frontend.
- [ONPC-CORE-RECOVERY-004] Invalid, unauthorized, denied or cancelled requests grant no time and relax no app policy. Remembered request choices may already reflect the last selection. A failed change is never presented as a success.
- [ONPC-CORE-RECOVERY-005] A failure before any apps are closed restores the previous settings and access state where rollback succeeds. Failure to verify restoration is reported as an error; the product does not claim recovery succeeded.
- [ONPC-CORE-RECOVERY-006] Closed apps cannot be reopened by rollback. If closing required apps fails or a later step fails after apps may have closed, already-closed apps stay closed. An app-policy save retains the requested saved block policy; approval and revocation preserve the prior time state while retaining the stricter app policy. The action reports failure, and other users remain unaffected.
- [ONPC-CORE-RECOVERY-007] A form refuses duplicate submissions while approval is pending. App-policy saves, approvals, revocations and session-entry reconciliation reject competing transactions. By default, a successful request starts a five-second cooldown for that requesting account; requests for different children from the request station share it. Denial and cancellation do not consume the cooldown. A request made too soon is refused before another authentication prompt.
- [ONPC-CORE-RECOVERY-008] Request failures show an actionable public error without system paths or backend error text. Authentication-agent failure ends that attempt without permanently disabling later requests. A retry can be made after the form/session is usable again.

### Product information

- [ONPC-CORE-ABOUT-001] A parent can open About, read the product name, installed version, copyright and GPL license information, open the installed license text, and return to the same selected child.
- [ONPC-CORE-ABOUT-002] About is also available from both request forms. It identifies the website, privacy notice, support address and legal notices. Parent and child-overlay links can open the browser, mail client or installed legal files. The dedicated request station displays this information without external launch links.
- [ONPC-CORE-ABOUT-003] Help in the Parent App and child overlay opens the product help website. The dedicated request station has no external Help action. Required information and actions remain reachable using normal focus, scrolling and window navigation. The installed commands `oh-no-parent-control-parent --help` and `oh-no-parent-control --help` show their usage without opening a product window; both also have installed command manuals.

### Feedback and error reports

- [ONPC-CORE-FEEDBACK-001] The Parent App offers Send Feedback. Product errors in the Parent App, Child App and request station can open an editable error report. Opening feedback or a report sends nothing; the user must select Send Feedback.
- [ONPC-CORE-FEEDBACK-002] The feedback editor accepts plain text and formatting: headings, bold, italic, underline, strikethrough, numbered and bulleted lists, quotes, code blocks and links, with a remove-formatting action. The reply email is optional. Empty feedback, malformed email, unsupported hidden characters, excessive text and excessive formatting receive an explanation without sending. The message limit is 5,000 UTF-16 units, so some emoji count as two.
- [ONPC-CORE-FEEDBACK-003] Ordinary feedback preserves its text, formatting, reply address and selected files when closed and reopened in the same Parent App process. If the embedded editor restarts, it restores the last text and formatting received by the app. Exiting the app discards the draft. Repeated errors do not overwrite an active error-report draft; closing that error report ends its draft.
- [ONPC-CORE-FEEDBACK-004] Opening feedback with diagnostics included displays collection progress. Editing and Close remain available; Send and file-attachment actions wait for collection. Collection failure offers Retry collection or explicit Send without logs; the latter submits the current valid draft without the diagnostic attachment. Reopening an ordinary draft refreshes diagnostics unless collection or sending is already in progress.
- [ONPC-CORE-FEEDBACK-005] Diagnostics are optional and initially included. The user can remove and add them again. Parent and child-overlay feedback can save the prepared ZIP to a chosen location for inspection. The download and current submission use the same prepared snapshot. Cancelling the save chooser keeps the draft and prepared logs; a failed save reports the problem and permits another location.
- [ONPC-CORE-FEEDBACK-006] Parent and child-overlay feedback can add and remove explicitly chosen files, showing their names and sizes. At most five files are accepted, each at most 5 MiB; all files plus diagnostics must total at most 8 MiB. Diagnostics alone are limited to 2 MiB. Filenames must be nonempty, at most 180 characters and free of hidden control characters. Cancelling a file chooser preserves the draft. If any file in a selection cannot be accepted, that selection adds no files and existing attachments remain. The app keeps the bytes read when files were added: later changes to the original files do not change the attachment unless it is removed and added again. Submission includes filenames and contents, not their original folder paths.
- [ONPC-CORE-FEEDBACK-007] Request-station feedback offers no Add files, editor attachment shortcut, diagnostic download or external privacy link. Its in-app privacy disclosure, optional diagnostics and explicit Send remain available without opening a general desktop.
- [ONPC-CORE-FEEDBACK-008] The Privacy action explains what feedback sends and that customer-written text, a reply email and selected files may contain personal information. It states that submissions are emailed to support and that mailbox/service-provider retention has no guaranteed fixed deletion period.
- [ONPC-CORE-FEEDBACK-009] Send freezes the selected content and attachments and prevents edits or duplicate sends until completion. Recoverable network/service failures show retry progress for up to 15 minutes while the app remains open. Automatic retries reuse the same submission identity and content. Closing ordinary feedback allows these retries to continue; exiting the app ends them.
- [ONPC-CORE-FEEDBACK-010] Confirmed acceptance by the feedback service clears the submitted draft, reply email and file attachments. If feedback is visible, it closes and shows a thank-you dialog until manually dismissed, with a follow-up note when a reply address was supplied. Background completion does not reopen a closed dialog. The confirmation reports service acceptance, not proof of email delivery to a recipient.
- [ONPC-CORE-FEEDBACK-011] Failed or oversized submissions preserve the draft for correction. An expired or stopped submission explains that an earlier attempt may have succeeded and that submitting again may duplicate it. There is no saved outbox that resumes after app exit.
- [ONPC-CORE-FEEDBACK-012] A request error offers “Report this error,” initially on. Closing the result reviews the report before leaving; turning the option off leaves directly. Successful requests and cancelled authentication do not offer this error-report step. Reports begin with a fixed public explanation and error categories that the user can edit.
- [ONPC-CORE-FEEDBACK-013] Closing an error report during submission offers “Stop sending and close,” ending pending retries before leaving. It cannot recall a request already accepted by the service. After successful sending, the user dismisses the thank-you dialog before the original error flow exits. If reporting cannot open, a simple error-report-unavailable message still allows exit.

### Diagnostics and privacy

- [ONPC-CORE-DIAGNOSTICS-001] The optional diagnostic archive contains a system-information summary and readable Parent, Child, Kiosk and Broker log folders. It includes each component's latest three available recorded dates, which may be nonconsecutive, and shows empty folders where no events exist. Older compatible reports without dates remain explicitly undated.
- [ONPC-CORE-DIAGNOSTICS-002] Automatic diagnostics contain validated technical events, timing and time-balance observations, service availability, software versions, timezone, session type and aggregate account counts. They exclude account names, account identifiers, email addresses, home paths, application inventories, personal file contents, raw system journals, passwords and raw exception messages. These exclusions do not apply to text and files the user deliberately supplies.
- [ONPC-CORE-DIAGNOSTICS-003] Diagnostic history is bounded. Collection reports unavailable or partial information, discarded records and limits rather than inventing missing data. The report is troubleshooting information, not a complete account-activity or security audit.
- [ONPC-CORE-DIAGNOSTICS-004] All three product roles may obtain the same bounded diagnostics from all four components. Child and request-station access does not expose arbitrary system files or private child preference files. Nothing is automatically uploaded.

### Updates, removal and reinstallation

- [ONPC-CORE-LIFECYCLE-001] A supported package upgrade preserves saved parent and request choices. The package applies the activation appropriate to changed components: new app processes, service restart, renewed child/request sessions, or a reboot notice. A parent can then reopen the relevant surfaces and verify the retained choices.
- [ONPC-CORE-LIFECYCLE-002] Saved-data conversion runs before the upgraded settings service starts. A conversion failure leaves the package configuration incomplete and the service unavailable, with the existing records retained for correction and retry. Newer, unreadable records are not silently replaced with defaults.
- [ONPC-CORE-LIFECYCLE-003] A parent can remove the package through normal package management after leaving the request-station session. Removal disables product time limits and app filters for recorded managed accounts, removes product execution rules and child activation, and removes the package-owned request-station account. It preserves personal accounts and unrelated administrator configuration. A conflict or cleanup failure is reported and prevents unverified cleanup from being treated as complete.
- [ONPC-CORE-LIFECYCLE-004] Ordinary removal retains saved child preferences and product logs for reinstallation. Reinstallation can display the retained choices; it does not recreate a removed one-time grant. Retained choices alone are not a promise that removal-cleared operating-system restrictions are automatically reapplied; parents can reapply screen-time settings and app rules in the Parent App.
- [ONPC-CORE-LIFECYCLE-005] Purge also deletes product-owned saved state and logs. It leaves dependency packages, their usage records, system journals and ordinary users' files under their existing owners. Reinstalling after purge starts with fresh parent-policy and shared request defaults; personal request-selector choices and the child's countdown-animation preference may remain.
- [ONPC-CORE-LIFECYCLE-006] Removal records a reboot requirement and normal APT removal prints the removal reboot notice. It does not force logout or reboot. Repeated cleanup preserves unrelated reboot requests and stops when package ownership cannot be verified.

## 2. Component specifications

These statements describe each component through the behavior it contributes.
Technical interfaces, storage formats and verification limits are in the
[system design](System-Design.md).

### Parent App

- [ONPC-COMP-PARENT-001] Gives local administrators management controls and refuses management-window startup for personal standard accounts. Launching Parent again presents its existing active window. Access or startup failure may show a reporting-only error window, with no management capability. The request-station account has no supported route to this window and cannot perform its management operations.
- [ONPC-COMP-PARENT-002] Selects one eligible child at a time and loads that child's settings and apps. New accounts appear during refresh without disturbing an existing valid selection. If the selection disappears, another available child is selected; with none, the app explains that no interactive standard account was found.
- [ONPC-COMP-PARENT-003] Screen Limits provides enablement, presets/custom allowance, current time and confirmed revocation. Expanding “How it's calculated” shows both remaining daily allowance and remaining one-time grant and explains that the larger applies, including when either is zero. With screen-time control off, a zero displayed total does not restrict access.
- [ONPC-COMP-PARENT-004] App Limits provides the child-specific app list, searchable descriptions, match/access filters, policy legend, access choices and match-rule editing.
- [ONPC-COMP-PARENT-005] Saves automatic changes in interaction order, with loading and conflicting operations guarded. Valid custom allowance edits save after a short pause, Enter or leaving the field. Match-rule drafts require Save or Reset to Default. A failed save reports the failure and rebuilds controls from the last confirmed choices, subject to the precise-rule limitation above. An irreversible app-closing failure follows the stricter-policy rule above, so reopening reloads the actual saved policy.
- [ONPC-COMP-PARENT-006] Manages policy and revokes grants. Additional time is approved through a child or request-station request. Help, About, ordinary feedback and error reporting remain separate from policy changes.

### Request station

- [ONPC-COMP-KIOSK-001] The installed dedicated session provides the request form and system authentication agent and returns to sign-in on exit. It offers no general desktop. The station account cannot be used for a different graphical session, terminal login or SSH login.
- [ONPC-COMP-KIOSK-002] Lists eligible children and parents, loads the chosen child's request preferences, and shows the estimated post-approval time described above.
- [ONPC-COMP-KIOSK-003] Submission waits for account lists and the selected child's settings. The form explains missing children, missing eligible parents and disabled screen-time control.
- [ONPC-COMP-KIOSK-004] Prevents duplicate submission or changes to the pending request while waiting for authentication.
- [ONPC-COMP-KIOSK-005] Submits the displayed child, parent, duration and soft-app choice; approval, denial, cancellation, errors and exit follow the shared rules.
- [ONPC-COMP-KIOSK-006] Remains restricted during requests, About and error reporting. It cannot manage daily allowances, app rules, accounts or system settings.

### Child app

- [ONPC-COMP-CHILD-001] The installed child component is activated for children whose screen-time control is on. When no desktop is running, that choice is retained for the next login; a live activation failure is reported instead of being accepted.
- [ONPC-COMP-CHILD-002] The remaining-time panel control appears only on the unlocked child desktop while usable time is positive. It is absent from sign-in and lock screens.
- [ONPC-COMP-CHILD-003] Combines the current daily-time estimate with the current grant. A temporary read failure retains the last verified estimate while time continues to elapse.
- [ONPC-COMP-CHILD-004] Opens one shared request overlay for the signed-in child, with eligible parent selection, remembered choices, time estimates, Help and About.
- [ONPC-COMP-CHILD-005] Refreshes after grant changes and closing the overlay, and requests expired-grant reconciliation at startup and after unlock. Failure is reportable and can be retried; the panel itself does not edit policy or close other apps.
- [ONPC-COMP-CHILD-006] Requests the normal desktop lock at zero time and repeats enforcement when needed. It does not log the child out or end another user's session.
- [ONPC-COMP-CHILD-007] Right-clicking the panel control opens “One minute count down animation,” initially off. Changing it is remembered for that child across login and reboot, independently of request-form sound preferences. This choice changes no allowance, grant, app rule or lock enforcement. There is no separate child settings window or product control embedded in the system lock screen. Child errors can open the shared Child App report.

### Broker

- [ONPC-COMP-BROKER-001] The background service supplies current account choices, child settings, app lists, time calculations, approvals, revocation and diagnostics to the product interfaces.
- [ONPC-COMP-BROKER-002] Uses the caller's actual system account for authorization, regardless of which executable made the request.
- [ONPC-COMP-BROKER-003] Rechecks selected children, approvers and saved choices during approval. A child request can target only the calling child.
- [ONPC-COMP-BROKER-004] Only administrators manage screen-time settings, app rules or revocation. The request station may request for an eligible selected child; an enabled child may request for itself. All time requests still require selected-parent approval.
- [ONPC-COMP-BROKER-005] Validates and stores private per-child settings and returns only role-authorized information. It does not let frontends directly edit those files.
- [ONPC-COMP-BROKER-006] Calculates remaining daily time from recorded use and combines it with grants according to the rules above. Invalid or unavailable inputs cause a reported failure, not invented free time.
- [ONPC-COMP-BROKER-007] Authenticates the selected parent for the displayed request and rejects stale approval when the requesting connection, account eligibility or relevant saved state changes.
- [ONPC-COMP-BROKER-008] Verifies reversible account changes and attempts rollback on failure. Closed processes cannot be restored; the stricter-policy and prior-time rules above apply. A failed rollback is a distinct error. Technical reload acknowledgements are limited as documented in the design.
- [ONPC-COMP-BROKER-009] Applies app policy only to the selected child. Expired nonzero grants trigger strict-policy reconciliation at session entry; an active replacement grant or absence of a recorded grant leaves the current policy and running apps unchanged.
- [ONPC-COMP-BROKER-010] Reconciles current app filters and enabled child activation before serving product operations. Separately, the operating system waits for initial execution-enforcement readiness before starting the graphical sign-in screen. Settings-service startup failure is reported to clients; it is not an additional sign-in-screen startup dependency.

## 3. End-to-end validation routes

These routes connect the requirements into ordinary customer journeys. Run each
applicable branch with the supported installed app; this table records no test
results. The [scenario recipes](TestAutomation/E2E-Scenario-Recipes.md) define
independent cases, complete finite matrices, reusable block sequences and the
separate owners of technical obligations. Use known child and parent accounts and an unrelated user's app where
isolation is being checked. Record displayed balances before changes and allow
for time spent navigating. Sign-out and reboot end windows; only retained
desktops can demonstrate an already-open app surviving a transition.

| Journey | Actions and observable results | Related scenario families |
| --- | --- | --- |
| Install and discover accounts | Install the package, read its notice and reboot. Sign in as a parent, open the Parent App and select a child. Check fresh defaults and both pages. Create another standard account through normal system settings; it appears while Parent remains open. A standard account cannot open management. | E2E-002–004; installation and account requirements |
| Validate and change allowances | Read the saved allowance while control is off, enable control, and exercise presets and custom values. Accept 0, 15 and 1439; reject 1440, negative, fractional, empty and nonnumeric values. Reopen Parent to confirm the last accepted value. With an active grant, change an enabled allowance and verify the grant keeps its deadline. Disable and re-enable control to check that the old grant does not return. | E2E-005; time, automatic-save and recovery requirements |
| Edit and enforce apps | Give the child enough time to use the desktop. In Parent, search/filter an app, inspect the legend and exercise match Save, Cancel and Reset. Open that app as the child and another user. Set the child's rule to blocked: the child's matching app closes and supported relaunches are denied; the other user's app continues. Repeat for soft/hard states and with screen-time control off. | E2E-006, 019–021; application requirements |
| Update the app list | Leave an app's match editor open, update or remove that app through normal package/file management, then save the rule. Reopen Parent to refresh the catalogue. Check the updated app's enforcement, or reinstall a removed app and inspect its retained rule. | E2E-020; catalogue and saved-match requirements |
| Daily exhaustion | Choose a short daily allowance with positive displayed time and no grant. Sign in as the child, use an allowed app and observe the countdown reaching zero naturally. The desktop locks; the correct password alone does not restore access. Where testing fresh login, use a legitimate grant to return and sign out, then revoke it before retrying with exhausted daily time. | E2E-008, 010–011; time and isolation requirements |
| Grant-only access from sign-in | Set daily allowance to zero and enable control. Observe the child's access denial. Enter the request station, choose that child, a parent, a short duration and the soft-app option. Review the matching system prompt and approve. The station returns to sign-in; the child can enter, use permitted apps and later reach expiry. | E2E-009, 016–017, 023; request, time and app requirements |
| More time from the desktop | While the child has time, open the panel request form twice and observe one fixed-child form. Try an invalid custom value, then a valid duration. Cancel authentication and retry; also check a denied attempt. On approval, compare the new balance with the larger prior balance plus the request. Exercise both soft-app choices and check their different effects on already-open apps. | E2E-012–015, 024–025; request and replacement-grant requirements |
| Revoke access | With an active grant and running child apps, return to Parent. Cancel one revocation and verify continued access. Confirm the next: blocked apps close and the grant disappears. Unused daily time still works; without it the child is restricted. Also check that Revoke remains available with positive daily time and no grant and leaves daily time intact. Visit the unrelated user's retained app to verify continuity. | E2E-007, 021, 036 and expired-grant E2E-038; pending qualification |
| Use the child panel options | While the child has time, read the panel and its hover explanation, open the right-click options and change the countdown-animation preference. Close the menu and use the normal request action. Sign out and back in with sufficient time and confirm the saved option; compare another child's independent choice. Acceptance checks availability, persistence and unchanged access, not animation appearance. | E2E-011 and E2E-037; pending qualification |
| Remember choices and resume | Set distinct duration/custom/soft-app choices for two children. Move between each overlay and the request station and read values before editing. Check each surface's own remembered parent selection and the absence of a mute control. Repeat through app closure, sign-out, reboot and suspend as applicable; grants retain their original deadline. Legacy interactive-mute cases remain deferred. | E2E-018, 022; persistence and current request-media requirements |
| About and feedback drafts | Open About and legal/help links where available, then return to the same parent selection or request form. In Parent feedback, edit/format synthetic text, try validation boundaries, inspect privacy, add/remove files and diagnostics, save a diagnostic ZIP and review it. Close/reopen to check the draft; exit/relaunch to check its reset. A naturally occurring error exercises the report-review/exit flow on its own surface. | E2E-030–031, 042, 045–047; added surface coverage remains pending |
| Feedback submission and retry | Only when sending is intended, explicitly submit a reviewed report to the actual service. Observe acceptance and manual dismissal of the thank-you dialog. For a real temporary network failure, restore connectivity within the retry window and observe automatic progress without pressing Send again. Service confirmation and recipient delivery are separate observations. | E2E-032–033; submission and retry requirements |
| Upgrade, remove and reinstall | Save distinct settings and request choices, install the update, complete the indicated activation and reread them. Leave the request station, remove the package, reboot as directed and verify ordinary child login/app use. Reinstall to inspect retained choices and reapply desired restrictions. Purge, then reinstall to observe fresh parent-policy and shared request defaults; personal selectors and countdown-animation choices may remain. | E2E-026–027; lifecycle requirements |
| Exercise input and account changes | Validate every daily preset and custom boundary, then save by pause, Enter and focus leave. Use normal Users settings to add/remove spare children or change an approver's eligibility. Observe Parent refresh and request-selector fallback before editing values. | E2E-035, 040–041 |
| Continue after a grant expires | Keep positive daily time when a soft-app grant expires. Check continued use, then separately exercise no restoring action, unlock, fresh login, allowance edit, toggle, unchanged app save and revocation. | E2E-038; seven distinct action outcomes |
| Leave approval pending and request again | Leave through a supported normal session/app action while the system approval prompt is open. Return and require a new request. Also attempt a prompt return during the five-second cooldown and retry after it ends. | E2E-039; unavailable public routes remain gated |
| Work offline and cross a day boundary | Disconnect through desktop controls and use local settings/approval/enforcement. In separately scheduled natural calendar windows, verify renewed daily allowance, local-midnight rest-of-day expiry and fixed elapsed grants across midnight or daylight-saving transitions. | E2E-043–044; no clock manipulation |

Technical checks separately cover identity races, malformed storage, partial
termination, failed rollback, service readiness and injected transport failures.
The pending E2E-028/029 declarations retain those engineering obligations; a
customer route does not replace or claim completion of them.
