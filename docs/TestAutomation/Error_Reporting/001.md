# Make product failures visible to the runner

Acceptance: installed
Targets: onpc-Ubuntu26.04, onpc-Fedora44

[Master plan](../Error_Reporting.md) · [Task queue](Task_Queue.md)

Define a small, privacy-safe failure event for the current product. Start at the
[logging design](../../SystemDesign/Logging-and-Feedback.md#logging) and its
[error-report paths](../../SystemDesign/Logging-and-Feedback.md#error-reports).
Trace the GTK, Shell and broker producers and their sink before changing them.
Use the existing diagnostic envelope or catalogue where it fits. Keep a short
set of semantic categories shared by report-triggering and log-only paths.
Emit before attempting UI presentation, at the point where the product treats
the condition as a fault. Normal cancellation, validation and defined denials
keep their existing meaning. Keep details such as exception text outside the
failure signal and follow the product's existing field provenance rules.

Qualify one broker-independent guest sink. A native structured journal record
is the first candidate. Verify delivery from the installed broker, Parent,
child extension, and kiosk paths, including front-end reporting while the
broker is unreachable. Verify a repeated fault is still observable after a
prior identical fault. Validate the component and boot against trusted source
metadata. Establish guest-side ordering that places the occurrence on the correct
side of a case boundary even when delivery is delayed. Define how the reader
lets pending writes settle and distinguishes a complete empty read from missing
or truncated evidence before teardown. Exercise delayed delivery and an
unavailable span in this qualification. Keep existing support diagnostics and
reporting behavior. For abrupt product exits, reuse a trusted OS failure record where the
existing observer attributes it to the product. Document the boundary for
failures that leave no attributable signal. If the first sink fails
qualification, diagnose that boundary and qualify a simpler supported route
with the same record contract before handoff.

Run the affected product checks and the queued package build after the final
build-affecting edit under the [repository mandates](../../../AGENTS.md).
Qualify actual product-emitted dialog and log-only faults through guarded
installed engineering checks on both named targets. Prefer extending an
existing check that owns the boundary. `check_product_failure_signal` is a
planned, unimplemented selector if a focused qualification is needed. Use the
[installed runner](../../../tests/integration/README.md#running-the-current-installed-suite)
and [VM ownership route](../../Mandates/VM-Mandate.MD#authority-and-operation).
Prove healthy actions emit no failure signal, qualifying faults remain
observable during an outage and on repeat, and public error reporting still
works. Finish owned cleanup. Record the exact selector used and document the
event and sink contract in the logging design for the next task.
