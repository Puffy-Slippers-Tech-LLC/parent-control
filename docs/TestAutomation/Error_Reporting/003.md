# Check for faults before every VM test passes

Acceptance: installed
Targets: onpc-Ubuntu26.04, onpc-Fedora44

[Master plan](../Error_Reporting.md) · [Task queue](Task_Queue.md)

Apply the shared verdict by default at the system pytest, VM-backed standalone
and E2E case boundaries. Include VM-backed installed checks explicitly selected
through `system CHECK` while preserving their aggregate eligibility. Start at
the [existing log capture](../../../tests/README.md#prompt-free-test-artifact-access),
[installed runner](../../../tests/integration/README.md#running-the-current-installed-suite),
[standalone inventory and dispatch](../../../tests/integration/README.md#aggregate-scheduling) and
[E2E reporting](../../../tests/e2e/README.md#public-execution-and-terminal-reporting).
Gate the published case verdict in all three routes. If a system controller has
case work left after guest pytest finishes, hold the pass until that work and
its observation also finish. Retain evidence before any owned shutdown or
snapshot restoration that would make it inaccessible. For rebooting cases,
account for each owned boot and continue onto the new one.
Start observation before case-owned actions can produce current-product faults,
including startup and clean installation where exercised by the case. In an
upgrade history, use existing package and session readiness checks to establish
and report the verified current-build interval. Bind work that the system
controller runs before or after pytest to the exact owning case. Discard stale
baseline and prior-case events. Product-free phases can complete with no
product events when the observation boundary is established.

Use the shared VM lease and guarded transport. Keep the verdict active with
Watch off. Read only the fault evidence needed for the owned interval at known
lifecycle boundaries. Reuse existing guest collection calls where they share
that boundary. Follow the [timing](../../Mandates/VM-Mandate.MD#timing-and-slow-vm-resilience)
and [storage](../../Mandates/Test-Storage-Mandate.md) contracts. Preserve the
original assertion failure and the lease's cleanup responsibilities. Update the
owning runner documentation with the case and failure-reporting contract.

Audit the installed execution paths and intentional fault cases before enabling
each route. Use case-owned allowances only where the case deliberately provokes
that category and asserts its intended result. Use the actual action and
recovery boundaries for asynchronous work and settle it through existing
observable state before evaluating recovery. Keep unrelated failures visible
throughout. Follow [failure handling](../../../tests/README.md#handling-test-failures)
for any additional faults found during rollout.

Run the lowest effective affected host checks. On `onpc-Ubuntu26.04`, run system
case `307` for broker crash and recovery. Verify that observation covers both
controller-owned fault and recovery histories before pytest starts. Run E2E
case `205` for the deliberate Parent report and restored rule, and
`system check_fixture_e2e_installed` for the registered standalone route. Run
`system check_fixture_e2e_installed` on `onpc-Fedora44` as well. Use
`tools/run-tests` with the exact selector and target for each invocation. The
cases must pass their original assertions and publish a verdict with complete
observation of the exercised current-code interval. Finish the checks directly
affected by allowance edits and apply the
[parallelism review](../../../tests/README.md#host-test-parallelism-review) for
resource-affecting changes. Join owned cleanup.
